# ADR-0005 — Separação obrigatória entre Server e Client Components usando server-only

**Status:** Aceito
**Sprint:** 1.3

## Contexto

`app/audience-intelligence/page.tsx` é um Client Component
(`"use client"`) que importa `lib/data.ts`. Antes da Sprint 1.3, isso
era seguro — `lib/data.ts` só continha arrays mockados. Ao introduzir
persistência via Prisma, `lib/data.ts` passou a re-exportar
`getPipelineModules`, que (transitivamente) depende de `@prisma/client`
e do driver `pg`.

## Problema

Como impedir que código exclusivo de servidor (Prisma, `pg`, drivers de
banco) vaze para o bundle do navegador — e, se isso acontecer de novo no
futuro, falhar de forma clara em vez de um erro críptico de bundler?

Este não é um problema hipotético: **ele aconteceu de verdade** durante
a Task 3 da Sprint 1.3. `npm run build` falhou com:

```
Module not found: Can't resolve 'net'
Module not found: Can't resolve 'tls'
```

— o bundler do navegador tentando resolver dependências Node-only do
`pg`, alcançadas via `app/audience-intelligence/page.tsx` → `lib/data.ts`
→ `lib/pipeline-core/store.ts` → `lib/pipeline-service` →
`lib/repositories` → `lib/db/client.ts` → `pg`.

## Decisão

1. Removido o re-export de `getPipelineModules` de `lib/data.ts` — o
   único consumidor real (`app/production/page.tsx`, um Server
   Component) passou a importar direto de `lib/pipeline-core/store`.
2. Adicionado `import "server-only"` em `lib/db/client.ts`,
   `lib/repositories/pipelineRepository.ts` e
   `lib/pipeline-service/pipelineService.ts` — o pacote oficial do
   Next.js que faz o build falhar explicitamente, com mensagem clara,
   se qualquer um desses arquivos for importado por um Client Component.

## Consequências

**Positivas**
- Build falha rápido e claro se a fronteira for violada de novo no
  futuro — em vez do erro genérico de "Module not found" que exige
  investigação manual (como aconteceu nesta Sprint).

**Negativas / trade-offs**
- O pacote `server-only` lança erro em **qualquer** execução Node fora
  do bundler do Next.js (inclusive Vitest e scripts via `tsx`) — só o
  webpack do Next.js sabe neutralizá-lo em contexto de servidor. Foi
  necessário criar um stub (`tests/mocks/server-only.ts`) e um alias no
  `vitest.config.ts` para os testes continuarem funcionando.

## Alternativas consideradas

- **Depender só de convenção/revisão de código.** Rejeitada — foi
  exatamente esse tipo de regressão acidental que quebrou o build nesta
  própria Sprint; convenção sem imposição automática não é suficiente.
- **`dynamic import()`/truques de lazy-loading para isolar o boundary.**
  Rejeitada por mais complexa do que necessário — `server-only` é a
  solução padrão e idiomática do ecossistema Next.js para exatamente
  este problema.

## Motivo da decisão

Esta ADR documenta um incidente real, não uma preocupação hipotética —
a fronteira Server/Client Component já quebrou uma vez nesta Sprint;
`server-only` transforma isso de um erro silencioso/tardio (só
descoberto no build) em uma falha imediata e legível.
