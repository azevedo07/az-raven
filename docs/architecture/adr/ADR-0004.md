# ADR-0004 — PipelineService é o único orquestrador entre Engine e Repository

**Status:** Aceito
**Sprint:** 1.2 (criação) / 1.3 (integração com persistência)

## Contexto

O estado do pipeline tem hoje dois tipos de consumidor: a UI existente
(via `lib/pipeline-core/store.ts`, chamada de função direta, sem HTTP) e
consumidores externos (via `app/api/pipeline/:projectId`). Ambos
precisam do mesmo comportamento consistente ao ler e, futuramente,
mutar o estado do pipeline.

## Problema

Como evitar lógica de orquestração duplicada (e divergente) entre os
dois consumidores, e como evitar que o `PipelineEngine` ou o
`PipelineRepository` precisem conhecer detalhes de quem os está
chamando?

## Decisão

`PipelineService` (`lib/pipeline-service/pipelineService.ts`) é o único
orquestrador entre `PipelineEngine` e `PipelineRepository`:

- É o único arquivo, além das próprias implementações de Engine e
  Repository, que importa ambos.
- Recebe o `PipelineRepository` via **injeção de dependência no
  construtor** (`constructor(private readonly repository: PipelineRepository)`),
  nunca instanciando `PrismaPipelineRepository` dentro da sua lógica.
- Não guarda mais um `Map` de engines em memória entre chamadas (decisão
  central da Sprint 1.3): cada operação reidrata o engine a partir do
  que o Repository retornar (`PipelineEngine.fromPersistedState`), aplica
  a ação, e persiste o resultado antes de retornar.
- É exportado como uma instância única já composta
  (`export const pipelineService = new PipelineService(new PrismaPipelineRepository())`)
  — o ponto de composição que `store.ts` e as rotas de API consomem.

## Consequências

**Positivas**
- Fonte única de verdade para "como ler/mutar o estado do pipeline" —
  sem lógica de seed/persistência duplicada entre `store.ts` e a rota de
  API.
- Ausência de estado em memória entre chamadas torna o processo
  corretamente escalável horizontalmente (múltiplas instâncias do
  servidor não divergem entre si).
- Testável isoladamente com um repositório falso em memória (injeção de
  dependência).

**Negativas / trade-offs**
- Uma consulta ao Repository (round-trip ao banco) a cada operação —
  trade-off deliberado em favor de corretude/escalabilidade horizontal
  em vez de otimização prematura. Um cache (ex.: Redis) fica
  documentado como otimização futura, não descartada.

## Alternativas consideradas

- **Cada consumidor falando direto com Engine + Repository.** Rejeitada:
  duplicação de lógica de seed/persistência, risco de divergência de
  comportamento entre UI e API.
- **Manter o `Map` de engines em memória (Sprint 1.1/1.2) como cache
  sobre o Repository.** Adiada, não rejeitada — pode voltar como
  otimização quando houver evidência real de necessidade de
  performance, uma vez conhecido o padrão de carga em produção.

## Motivo da decisão

Um único ponto de orquestração simplifica o raciocínio sobre o sistema,
os testes (injeção de repositório falso) e a extensão futura (novos
casos de uso tocam só esta classe).
