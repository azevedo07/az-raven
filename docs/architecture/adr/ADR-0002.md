# ADR-0002 — Repository Pattern usando Prisma

**Status:** Aceito
**Sprint:** 1.3

## Contexto

A Sprint 1.3 precisava dar persistência real ao estado do
`PipelineEngine` (hoje só em memória, perdido a cada restart). Uma
análise comparativa prévia (bancos: PostgreSQL, MySQL, SQLite, MongoDB;
ORMs: Prisma, Drizzle, TypeORM) recomendou **PostgreSQL + Prisma** como
arquitetura oficial, considerando escalabilidade, integração com
Next.js/TypeScript, maturidade de migração, comunidade e suporte de
longo prazo para um projeto planejado para durar anos.

## Problema

Como persistir o estado do Engine sem acoplar o `PipelineEngine` nem o
`PipelineService` a uma tecnologia de ORM/banco específica — de forma
que trocar Prisma por outra solução no futuro seja uma mudança contida,
não uma reescrita?

## Decisão

Introduzido o **Repository Pattern**:

- `PipelineRepository` (`lib/repositories/types.ts`) — contrato puro
  (interface), sem nenhuma dependência de `@prisma/client`.
- `PrismaPipelineRepository` (`lib/repositories/pipelineRepository.ts`)
  — implementação concreta. Junto com `lib/db/client.ts` (o singleton do
  Prisma Client), são os **únicos** arquivos do projeto que importam
  `@prisma/client` diretamente.
- O `PipelineService` depende só da interface `PipelineRepository`,
  nunca da implementação Prisma diretamente (ver ADR-0004).

## Consequências

**Positivas**
- Troca de ORM fica contida em `lib/repositories/` — Service, Engine,
  API e UI não precisam mudar.
- Testável com um repositório falso em memória
  (`FakePipelineRepository`, usado em `tests/pipeline-service/`), sem
  exigir um Postgres real para testes de lógica de negócio.

**Negativas / trade-offs**
- Indireção extra para operações simples de CRUD.
- `PipelineExecution.projectId` é uma foreign key obrigatória para
  `Project.id` — o projeto de demonstração "o-corvo" (originalmente só
  um identificador mockado em `lib/data.ts`) precisou de um script de
  seed (`prisma/seed.ts`) para existir como uma linha real de `Project`
  antes de qualquer persistência de pipeline funcionar.

## Alternativas consideradas

- **Prisma direto dentro do `PipelineService`.** Rejeitada: violaria a
  separação de camadas, dificultaria testes e acoplaria a lógica de
  orquestração a uma tecnologia de persistência específica.
- **Drizzle ORM em vez de Prisma.** Considerada seriamente na análise
  comparativa — Drizzle vence em desempenho bruto e leveza serverless.
  Prisma venceu pela combinação de DX, tamanho de comunidade,
  maturidade de tooling de migração e integração documentada com
  Next.js, fatores que pesam mais para um projeto que precisa durar
  "muitos anos" com equipe evoluindo ao longo do tempo.

## Motivo da decisão

Inversão de dependência (Service depende da interface, não da
implementação) é o que protege o resto da arquitetura de churn
tecnológico na camada de persistência — e mantém a mesma disciplina de
fronteiras já estabelecida entre Engine e Registry.
