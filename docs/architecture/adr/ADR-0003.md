# ADR-0003 — Cada Project possui exatamente uma PipelineExecution

**Status:** Aceito (**provisório** — revisão planejada, ver "Consequências")
**Sprint:** 1.3

## Contexto

O schema do Prisma modela `PipelineExecution` com uma foreign key
obrigatória para `Project` (`projectId`), mas **sem** uma restrição de
unicidade nesse campo — o schema, hoje, permite tecnicamente múltiplas
`PipelineExecution` por projeto.

## Problema

O `PipelineRepository` precisa de uma forma determinística de decidir
qual `PipelineExecution` representa "o estado atual" do pipeline de um
projeto, para `findState`/`saveState` funcionarem sem ambiguidade.

## Decisão

`PrismaPipelineRepository` trata a `PipelineExecution` **mais recente**
(`orderBy: createdAt desc`) como a execução canônica/atual de um
projeto. Esta é uma **convenção da camada de aplicação**, não uma
restrição do banco de dados.

## Consequências

**Positivas**
- Simples, não exige migração de schema agora.
- Deixa em aberto a possibilidade de o domínio precisar de múltiplas
  execuções por projeto no futuro (ex.: reprocessamento, histórico de
  tentativas) antes de travar essa decisão em uma restrição rígida.

**Negativas / trade-offs**
- Nada no nível do banco impede, hoje, que um bug ou uma condição de
  corrida crie duas execuções "concorrentes" para o mesmo projeto,
  gerando ambiguidade sobre qual é "a atual".
- **Esta decisão é explicitamente provisória.** Registrado no momento
  da aprovação da Task 2 (Sprint 1.3): *"a convenção de considerar a
  PipelineExecution mais recente como 'a atual' fica aceita nesta
  Sprint, mas deve permanecer documentada como uma decisão provisória
  de implementação. Em uma Sprint futura avaliaremos se o domínio deve
  permitir múltiplas PipelineExecution por projeto ou se haverá uma
  restrição de unicidade no schema."*

## Alternativas consideradas

- **Adicionar `@@unique([projectId])` a `PipelineExecution` agora.**
  Rejeitada por prematura — o domínio ainda não tem um caso de uso
  concreto que exija decidir entre "uma execução para sempre" ou
  "múltiplas execuções versionadas" por projeto.
- **Bloqueio/transação a nível de aplicação para garantir singularidade.**
  Rejeitada por adicionar complexidade sem necessidade demonstrada.

## Motivo da decisão

Permite que a Sprint 1.3 entregasse persistência funcional sem forçar
uma decisão de modelagem que ainda não tem evidência suficiente — mas
exige que essa lacuna fique documentada e visível, não silenciosamente
esquecida.
